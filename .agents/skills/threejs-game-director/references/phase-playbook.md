# Director Phase Playbook

Use selected sections for explicitly requested whole-game or named multi-system
work. Root `AGENTS.md` owns scope, authority and verification. Phases are choices
based on dependencies, not a required tour of every skill. Reuse decisions and
evidence already established in the task.

## Frame the outcome

For a new game, establish the player promise, primary verbs, objective, pressure,
progression and resume/retry behavior. Include only systems the brief needs.
For an existing game, trace the requested improvement to current owners and
callers; preserve its identity and contracts. In Neva, the design already lives
in `01`, `02` and `04`, and `03` owns milestone order.

A compact dependency plan can help long work. Track unresolved choices,
integration dependencies and evidence gaps when useful; four separate ledgers
and reference-loading reports are unnecessary.

## Gameplay

Read the sibling `threejs-gameplay-systems/SKILL.md` and select references by
the changed mechanic, level design, input/physics or game-feel question. Build
playable increments through the existing simulation and presentation boundaries.
Exercise the changed input, outcome, failure and resume paths. Do not invent
combat, scoring or fail states merely because a template includes them.

Only new empty projects may use the gameplay scaffold after checking its fit.
Neva uses its existing source, scripts, tests and runtime hooks.

## Graphics and assets

Use `threejs-skill-router` for a specific mechanism, or
`threejs-aaa-graphics-builder` for the requested visual pass. Establish the
visible mismatch against the current brief, implement in the owning system,
inspect at gameplay distance and correct scoped defects. Form, spacing and
material response matter more than compulsory detail or effects.

Select suitable existing, procedural or explicitly authorized external sources.
No provider output or credential probe is required to justify procedural work.
If provider generation is requested, load that generator's instructions, retain
provenance and integrate through the project pipeline. Neva static assets use
the registered Blender/catalog path; a downloaded GLB is never direct runtime
publication. Audio work uses existing cues and lifecycle owners before deciding
whether new source files are needed.

Evidence follows the affected contract: changed views/motion, relevant resource
measurements and observed limitations. `04` §19 governs Neva visual acceptance;
the pack's critique references do not impose a numerical threshold or universal
enemy/reward/density checklist.

## UI

Use `threejs-game-ui-designer` for affected surfaces. Preserve actual state and
DTO ownership, verify readable real content and interaction, and test the
viewports and input modes the task affects. Do not redesign every menu because
one HUD control needs work. Generating icons or backgrounds remains a separately
authorized source choice, not a UI quality prerequisite.

## Diagnosis and performance

Use `threejs-debug-profiler` when reproduction or measurement is needed. Fix
the owner of the demonstrated cause; retest the failing caller path. Compare
matching scenarios, quality tiers and build modes. A passing nearby test, a
nonblank canvas or a screenshot does not establish gameplay or performance.

## Release and handoff

Use `threejs-qa-release` for a requested release or visual-gold gate. Ordinary
verification uses `03` §4 directly. Reuse the project's harness; add coverage only
for a meaningful regression risk. Keep human approval, mechanical publication,
production measurements and hosted deployment distinct.

Report the requested result, relevant evidence and remaining gaps in the project
completion format (`03` §30 in Neva). Do not add a report validator, fixed
scorecard, mandatory reviewer or a request to change models. Delegate only when
authorized, with bounded ownership and integration review.
